# Schedule configuration: Quartz vs application config

Short answer: Quartz already persists scheduling state in its own tables (QRTZ_*). You do not need a separate `scheduler_config` table unless your application requires business metadata or UI-specific fields that Quartz does not model.

This document explains when to rely on Quartz alone, when to add an application-level config table, and provides practical examples and patterns.

## What Quartz stores (JDBC JobStore)

Quartz manages its internal state in tables such as:

- `QRTZ_JOB_DETAILS` — job definitions
- `QRTZ_TRIGGERS` — trigger metadata
- `QRTZ_CRON_TRIGGERS` — cron expressions
- `QRTZ_FIRED_TRIGGERS` — currently executing triggers
- `QRTZ_SCHEDULER_STATE` — scheduler instance state
- `QRTZ_LOCKS` — cluster coordination

If you use the JDBC JobStore, calls like `scheduler.rescheduleJob(triggerKey, newTrigger)` persist directly into these tables.

## When Quartz alone is enough

Use Quartz by itself when:

- You have a fixed set of job types (e.g. `TRANSACTION_STATUS_CHECK`, `RECONCILIATION`).
- You only need to change execution timing (cron/interval) and read trigger metadata (next fire time, previous fire time).
- Business metadata (who changed it, description, tags) is not needed in your UI or reports.

Pattern: store job identity in your code (enum or config), and let Quartz store the schedule. Example startup flow:

1. Application starts and registers JobDetails and default Triggers with Quartz.
2. Admin calls `scheduler.rescheduleJob(...)` to change timings at runtime.
3. Quartz persists changes in `QRTZ_*` tables.

You can read trigger info via `scheduler.getTrigger(triggerKey)` to display next run time, state, etc., in your UI.

## When to add `scheduler_config` (application-level table)

Add an application table when you need business or audit data associated with a schedule that Quartz isn't meant to hold, for example:

- `description`, `business_name`, `created_by`, `updated_by`, `change_reason`.
- Multi-tenant or user-specific configs linked to business objects.
- Searchable UI listing with business fields and permissions.

Sample schema (Postgres):

```sql
CREATE TABLE scheduler_config (
  id BIGSERIAL PRIMARY KEY,
  job_type TEXT NOT NULL,
  business_name TEXT,
  description TEXT,
  enabled BOOLEAN DEFAULT TRUE,
  created_by TEXT,
  updated_by TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);
```

In this model, Quartz still owns timing and execution state; your `scheduler_config` table owns business metadata and audit fields. The ScheduleService maps `scheduler_config.id` → `JobKey/TriggerKey` when creating jobs.

## Pros & cons

- Quartz-only
  - Pros: simpler, fewer custom tables, Quartz handles persistence and clustering.
  - Cons: limited business metadata and auditability; UI may need to query Quartz tables directly.

- Quartz + `scheduler_config`
  - Pros: clean separation of business metadata, easier UI and audit, safer to evolve business fields.
  - Cons: additional table and mapping logic; need to keep DB + Quartz in sync.

## Example patterns

- Keys: use consistent keys (`job:{id}` / `trigger:{id}`) where `id` is your `scheduler_config.id` or a stable identifier.
- Create flow (with app table): save `scheduler_config` → create `JobDetail` + `Trigger` with keys containing the saved `id` → `scheduler.scheduleJob(...)`.
- Update flow (Quartz-only): directly call `scheduler.rescheduleJob(triggerKey, newTrigger)` and read trigger info from Quartz.

## API & UI considerations

If you rely on Quartz-only, the API should read scheduling metadata from Quartz (`scheduler.getTrigger(...)`, `scheduler.getTriggerState(...)`) to populate the UI. If you use `scheduler_config`, read from your table and enrich with trigger state from Quartz.

Recommended admin endpoints:

```
GET    /api/schedules
GET    /api/schedules/{id}
POST   /api/schedules
PUT    /api/schedules/{id}
DELETE /api/schedules/{id}
POST   /api/schedules/{id}/pause
POST   /api/schedules/{id}/resume
POST   /api/schedules/{id}/trigger
```

## Practical tips

- If you choose Quartz-only, avoid querying QRTZ_* tables from business code — prefer the Quartz API to keep portability.
- Keep `JobDataMap` small; store large payloads in your application DB and pass IDs.
- To avoid race conditions: persist app config first (if using `scheduler_config`), then schedule the job with Quartz in the same or coordinated transaction.
- Use durable JobDetails and persistent JobStore for production and clustering.

## Quick decision checklist

- Do you need business metadata, audit, or rich UI listings? → Add `scheduler_config`.
- Do you only need to change timing for a fixed set of job types? → Quartz-only is fine.
- Will multiple app instances run in Kubernetes? → Use JDBC JobStore and clustering.
