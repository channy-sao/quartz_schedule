
# Quartz — concise guide

Quartz is a production-ready job scheduler for Java. It answers "when should this code execute?" and provides tools to schedule, persist, coordinate, and operate jobs in single-node or clustered environments.

**Core strengths:** flexible triggers (cron/interval/one-shot), optional JDBC persistence, clustering across nodes, and runtime controls (pause/resume/manual trigger).

## Quick start (Spring Boot)

Add the starter dependency:

```xml
<dependency>
       <groupId>org.springframework.boot</groupId>
       <artifactId>spring-boot-starter-quartz</artifactId>
</dependency>
```

Minimal `application.yml` examples:

```yaml
# quartz basic
spring:
       quartz:
              job-store-type: jdbc
              jdbc:
                     initialize-schema: always
              properties:
                     org:
                            quartz:
                                   scheduler:
                                          instanceName: MyScheduler
                                   threadPool.threadCount: 5

# datasource (Postgres example)
spring:
       datasource:
              url: jdbc:postgresql://db:5432/quartz
              username: quartz
              password: secret
              driver-class-name: org.postgresql.Driver
```

Tip: use `spring.quartz.job-store-type=jdbc` to enable persistence, then configure the DB and run Quartz schema SQL (bundled with Quartz) for PostgreSQL.

## Core concepts

- `Job`: the work unit (class implementing `Job` or extending `QuartzJobBean`).
- `JobDetail`: job definition (identity, durability, JobDataMap).
- `Trigger`: schedule (cron, simple interval, calendar-based).
- `Scheduler`: manager that registers JobDetails + Triggers and executes jobs.

Example Job (Spring integration):

```java
public class MyJob extends QuartzJobBean {
       @Override
       protected void executeInternal(JobExecutionContext ctx) {
              // business logic
       }
}
```

Programmatic Job + Trigger:

```java
JobDetail job = JobBuilder.newJob(MyJob.class)
              .withIdentity("myJob")
              .build();

Trigger trigger = TriggerBuilder.newTrigger()
              .withSchedule(CronScheduleBuilder.cronSchedule("0 0/5 * * * ?"))
              .build();
```

## Cron & common patterns

- Every 10 seconds: `0/10 * * * * ?`
- Every 5 minutes: `0 0/5 * * * ?`
- Every hour: `0 0 * * * ?`
- Daily at 01:00: `0 0 1 * * ?`
- Daily at 23:30: `0 30 23 * * ?`
- Mondays at 08:00: `0 0 8 ? * MON`

Use cron triggers for rich schedules; use simple triggers for fixed delays/intervals.

## Scheduling modes

- One-shot: schedule a job to run once at a specific date/time.
- Repeating: cron or fixed-interval triggers.
- Dynamic: create, reschedule, or remove triggers at runtime (DB-driven or admin UI).

Example: create triggers from DB rows representing future execution times (ideal for per-transaction scheduling).

## Dynamic scheduling & administration

- Expose admin endpoints to `create`, `reschedule`, `pause`, `resume`, `trigger now`, and `delete` jobs.
- Example manual trigger API: `POST /admin/jobs/{jobKey}/trigger`.
- Allow admins to modify: cron expression, enabled flag, start/end time.

## Passing parameters to jobs

Use `JobDataMap` to pass small values into a job:

```java
JobDataMap data = new JobDataMap();
data.put("transactionId", "TX12345");

JobDetail job = JobBuilder.newJob(MyJob.class)
              .usingJobData(data)
              .build();

// inside job
String tx = context.getMergedJobDataMap().getString("transactionId");
```

Store larger payloads (documents, blobs) externally and pass references (IDs) to the job.

## Retries and failure handling

- Quartz schedules and runs jobs; implement retry/backoff logic inside the job or use a wrapper that reschedules on failure.
- Track status (`PENDING`, `PROCESSING`, `FAILED`) in your DB and schedule compensating jobs when needed.

Example backoff flow:

1. Attempt → fail
2. Reschedule or schedule a retry trigger after a delay
3. Continue until max attempts reached

## Concurrency and guarantees

- Use `@DisallowConcurrentExecution` on a job class to prevent overlapping executions for the same JobDetail.
- Keep jobs idempotent to tolerate retries and accidental duplicates.

Example:

```java
@DisallowConcurrentExecution
public class PaymentJob extends QuartzJobBean { ... }
```

## Persistence, clustering, and Kubernetes

- For resilience and clustering, use the JDBC JobStore with a shared DB (Postgres, MySQL, etc.).
- In Kubernetes, run multiple pods pointing to the same job store; Quartz will coordinate via DB locking so only one instance executes a given trigger.

Diagram (conceptual):

```
                                           PostgreSQL
                                                         │
                            ┌────────┼────────┐
                            │        │        │
                     Pod 1    Pod 2    Pod 3
                            │        │        │
                            └────────┼────────┘
                                                         │
                                                 Quartz
```

## Misfires (missed executions)

When a scheduled fire is missed (application down, long GC), Quartz offers misfire instructions per trigger type: e.g. execute immediately, skip, or follow next schedule. Configure misfire policies appropriate to each job's semantics.

## Cheatsheet & adoption checklist

- Dependency: add `spring-boot-starter-quartz`.
- Persistence: enable JDBC JobStore and run Quartz schema for your DB.
- Concurrency: use `@DisallowConcurrentExecution` where needed.
- Monitoring: add metrics and alerts for job failures and long-running executions.
- Admin APIs: expose create/reschedule/pause/resume/trigger/delete endpoints.
- Jobs: keep small, idempotent, and quick; hand off long jobs to worker queues if needed.

## 17. Possibility #14 — Prevent concurrent execution  
Suppose the scheduler runs every minute:  
```

10:00 → Job starts
10:01 → Job still running


```
Without protection, another execution could start.  
Quartz provides mechanisms such as:  
```

@DisallowConcurrentExecution


```
Example:  
```

@DisallowConcurrentExecution
public class PaymentJob extends QuartzJobBean {

    @Override
    protected void executeInternal(JobExecutionContext context) {
        // process
    }
}


```
This tells Quartz that executions of the same job detail should not overlap.

## 20. Possibility #17 — Persistent jobs  
This is extremely important.  
By default, you could have:  
```

Application
    ↓
Quartz
    ↓
Memory


```
If the application restarts:  
```

Application restart
       ↓
Memory cleared
       ↓
Jobs may disappear


```
Quartz can instead use a database:  
```

Spring Boot
     ↓
Quartz
     ↓
PostgreSQL


```
Then jobs and triggers can survive application restarts.  
  
## 21. Possibility #18 — Kubernetes clustering  
This is probably particularly relevant to your environment.  
Suppose you deploy:  
```

Kubernetes
│
├── Pod 1
│    └── Spring Boot + Quartz
│
├── Pod 2
│    └── Spring Boot + Quartz
│
└── Pod 3
     └── Spring Boot + Quartz


```
You don't necessarily want:  
```

Pod 1 → Execute Job
Pod 2 → Execute Job
Pod 3 → Execute Job


```
because that could execute the same business operation three times.  
Quartz supports clustered scheduling with a shared database:  
```

             PostgreSQL
                 │
        ┌────────┼────────┐
        │        │        │
      Pod 1    Pod 2    Pod 3
        │        │        │
        └────────┼────────┘
                 │
              Quartz


```
Quartz uses database coordination/locking so that a scheduled execution is acquired by one cluster node.  
  
## 22. Possibility #19 — Survive application restart

```
Every day at 01:00

```

## 23. Possibility #20 — Misfire handling  
This is a very important Quartz feature.  
Suppose:  
```

Job scheduled → 01:00


```
But your application is down:  
```

00:50 → application down
01:00 → job should execute
01:30 → application starts


```
Quartz needs to decide:  
What should happen to the missed 01:00 execution?  
This is called a **misfire**.  
Possible strategies include:  
```

Execute immediately
Skip the missed execution
Execute according to the next schedule


```
This is very useful for production systems.

## 39. Quartz database tables  
When using JDBC JobStore, Quartz creates tables such as:  
```

QRTZ_JOB_DETAILS
QRTZ_TRIGGERS
QRTZ_CRON_TRIGGERS
QRTZ_SIMPLE_TRIGGERS
QRTZ_FIRED_TRIGGERS
QRTZ_SCHEDULER_STATE
QRTZ_LOCKS
...


```
These tables maintain scheduler state.  
For a production application, you normally shouldn't manually manipulate these tables. Use Quartz's API.  
  
## 40. Quartz configuration in Spring Boot  
A basic configuration could be:  
```

spring:
  quartz:
    job-store-type: jdbc

    jdbc:
      initialize-schema: never

    properties:
      org:
        quartz:
          scheduler:
            instanceName: MyScheduler
            instanceId: AUTO

          jobStore:
            class: org.quartz.impl.jdbcjobstore.JobStoreTX
            driverDelegateClass: org.quartz.impl.jdbcjobstore.PostgreSQLDelegate
            tablePrefix: QRTZ_
            isClustered: true
            clusterCheckinInterval: 10000

          threadPool:
            class: org.quartz.simpl.SimpleThreadPool
            threadCount: 10
            threadPriority: 5


```
The exact configuration depends on your Spring Boot/Quartz versions and deployment architecture.  
  
## 41. Quartz thread pool  
Quartz has worker threads.  
For example:  
```

Quartz
   │
   ├── Thread 1 → Job A
   ├── Thread 2 → Job B
   ├── Thread 3 → Job C
   └── Thread 4 → Job D


```
Suppose:  
```

threadCount: 10


```
Quartz can have up to roughly 10 worker threads executing jobs concurrently, subject to the scheduler/job constraints.  
You need to size this carefully.  
For example, don't create:  
```

1000 Quartz threads


```
just because you have 1000 jobs.  
  
## 42. Quartz is NOT a message queue  
This is important.  
Quartz is good for:  
```

"When should this job execute?"


```
Kafka/RabbitMQ/etc. are better for:  
```

"How should I distribute/process these messages?"


```
For example:  
```

Quartz
  ↓
Every 5 minutes
  ↓
Publish message
  ↓
Kafka
  ↓
Workers


```
This is a very good architecture for large workloads.

## 46. When I would NOT use Quartz  
Don't automatically add Quartz just because you need a scheduled task.  
For something simple:  
```

@Scheduled(fixedRate = 300000)


```
is much easier.  
For example:  
```

Every 5 minutes
   ↓
Clear local cache


```
No need to introduce Quartz if you don't need its advanced features.  
Likewise, if you have massive workloads:  
```

10 million records


```
Quartz should probably **trigger** a batch/worker process rather than perform all 10 million operations itself.  
  
## 47. The biggest advantages of Quartz  
In summary, Quartz can provide:  
```

                    QUARTZ
                       │
 ┌─────────────────────┼─────────────────────┐
 │                     │                     │
Scheduling          Persistence           Clustering
 │                     │                     │
Cron                 Database             Kubernetes
Intervals            Recovery             Multi-pod
One-time             Restart-safe         Coordination
 │
 ├── Dynamic scheduling
 ├── Pause / Resume
 ├── Manual trigger
 ├── Delete jobs
 ├── Retry strategies
 ├── Misfire handling
 ├── Job parameters
 ├── Concurrent execution control
 ├── Priorities
 ├── Time zones
 ├── Job listeners
 └── Trigger listeners


```
For **your Spring Boot microservice running on Kubernetes**, the most valuable Quartz features would likely be **persistent JDBC scheduling + clustering + dynamic scheduling + transaction-status polling + reconciliation + misfire handling**. Those are the areas where Quartz provides substantially more value than a simple @Scheduled method.
