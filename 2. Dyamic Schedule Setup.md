# Dynamic schedule setup

This document shows a compact, production-oriented approach to letting users create, update, and manage Quartz schedules at runtime (without redeploys). It includes architecture guidance, a sample DB schema, Spring Boot + Quartz code snippets (service & controller), and operational considerations.

## Goals

- Allow users to create and change schedules from an admin UI.
- Persist configurations in the database so schedules survive restarts.
- Support cron, simple-interval, and one-shot schedules.
- Enable enable/disable, start/end windows, timezone-aware scheduling, and manual triggering.

## Architecture (recommended)

Frontend / Admin UI → Schedule Management API → Schedule Service → PostgreSQL (config) + Quartz Scheduler → Jobs → Business Logic

Store user-visible configuration in the DB; the Schedule Service translates config to Quartz JobDetails and Triggers.

## Example DB schema (PostgreSQL)

```sql
CREATE TABLE schedule_config (
  id BIGSERIAL PRIMARY KEY,
  user_id UUID NULL,
  name TEXT NOT NULL,
  job_type TEXT NOT NULL,
  cron_expression TEXT NULL,
  timezone TEXT NULL,
  start_time TIMESTAMP NULL,
  end_time TIMESTAMP NULL,
  repeat_count INT NULL,
  payload JSONB NULL,
  enabled BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);
```

Notes:
- `job_type` identifies which Job class to run (or which handler to call).
- `payload` stores small JSON references (IDs, params); avoid storing large blobs.

## Naming conventions

- JobKey: `job:{id}`
- TriggerKey: `trigger:{id}`

Using the DB `id` in keys simplifies rescheduling and lookup.

## Flow: create schedule (high level)

1. Client sends POST `/api/schedules` with config (jobType, cron/interval, timezone, start/end, payload).
2. API validates and writes a row to `schedule_config`.
3. Schedule Service creates a `JobDetail` and `Trigger` for the saved `id` and calls `scheduler.scheduleJob(jobDetail, trigger)`.
4. Quartz runs the job according to the trigger until disabled or removed.

## Example — scheduling service (Spring + Quartz)

```java
@Service
public class ScheduleService {
  private final Scheduler scheduler; // org.quartz.Scheduler

  public ScheduleService(Scheduler scheduler) { this.scheduler = scheduler; }

  public void schedule(long id, String jobType, String cronExpr, String timezone, Map<String,Object> data) throws SchedulerException {
    JobKey jobKey = JobKey.jobKey("job:" + id);
    JobDataMap jobData = new JobDataMap(data);
    JobDetail job = JobBuilder.newJob(resolveJobClass(jobType))
        .withIdentity(jobKey)
        .usingJobData(jobData)
        .build();

    TriggerKey triggerKey = TriggerKey.triggerKey("trigger:" + id);
    CronScheduleBuilder cron = CronScheduleBuilder.cronSchedule(cronExpr)
        .inTimeZone(TimeZone.getTimeZone(timezone));

    Trigger trigger = TriggerBuilder.newTrigger()
        .withIdentity(triggerKey)
        .forJob(job)
        .withSchedule(cron)
        .build();

    // If job already exists, reschedule
    if (scheduler.checkExists(jobKey)) {
      scheduler.addJob(job, true, true);
      scheduler.rescheduleJob(triggerKey, trigger);
    } else {
      scheduler.scheduleJob(job, trigger);
    }
  }

  private Class<? extends Job> resolveJobClass(String jobType) {
    // map jobType to Job class
  }
}
```

Notes:
- `addJob(..., true, true)` will update the stored JobDetail if the definition changed.
- `rescheduleJob(triggerKey, newTrigger)` updates an existing trigger.

## Example — controller endpoints

```java
@RestController
@RequestMapping("/api/schedules")
public class ScheduleController {
  private final ScheduleService scheduleService;
  private final ScheduleConfigRepository repo; // saves to DB

  @PostMapping
  public ResponseEntity<?> create(@RequestBody ScheduleDto dto) {
    ScheduleConfig saved = repo.save(dto.toEntity());
    scheduleService.schedule(saved.getId(), saved.getJobType(), saved.getCronExpression(), saved.getTimezone(), dto.getPayload());
    return ResponseEntity.created(...).body(saved);
  }

  @PutMapping("/{id}")
  public ResponseEntity<?> update(@PathVariable long id, @RequestBody ScheduleDto dto) {
    ScheduleConfig existing = repo.findById(id).orElseThrow(...);
    existing.updateFrom(dto);
    repo.save(existing);
    scheduleService.schedule(existing.getId(), existing.getJobType(), existing.getCronExpression(), existing.getTimezone(), dto.getPayload());
    return ResponseEntity.ok(existing);
  }

  @PostMapping("/{id}/trigger")
  public ResponseEntity<?> triggerNow(@PathVariable long id) {
    scheduleService.triggerNow(id);
    return ResponseEntity.accepted().build();
  }

  @DeleteMapping("/{id}")
  public ResponseEntity<?> delete(@PathVariable long id) {
    scheduleService.delete(id);
    repo.deleteById(id);
    return ResponseEntity.noContent().build();
  }
}
```

## Operations: pause / resume / delete / trigger

- Pause: `scheduler.pauseTrigger(triggerKey)` or `scheduler.pauseJob(jobKey)`.
- Resume: `scheduler.resumeTrigger(triggerKey)` or `scheduler.resumeJob(jobKey)`.
- Delete: `scheduler.deleteJob(jobKey)` (removes job and triggers).
- Trigger now: `scheduler.triggerJob(jobKey, jobDataMap)`.

Implement these in `ScheduleService` and call from admin endpoints.

## One-shot jobs, start/end windows, and repeat counts

- One-shot: create a `SimpleTrigger` or `Date`-based trigger for a single fire time.
- Start/End window: set `startAt(...)` and `endAt(...)` on the trigger builder.
- Max executions: use `withSchedule(SimpleScheduleBuilder.repeatSecondlyForever(...).withRepeatCount(n))` or track executions in your DB and cancel when reached.

## Timezones

- Store the timezone with the schedule and apply it via `CronScheduleBuilder.inTimeZone(...)` so triggers fire at local times.

## Misfires and reliability

- Configure misfire instructions appropriate to the job: e.g. `withMisfireHandlingInstructionFireAndProceed()` or `withMisfireHandlingInstructionDoNothing()` depending on semantics.
- For important business operations, prefer durable job definitions and persistent JDBC JobStore.

## Concurrency and idempotency

- Use `@DisallowConcurrentExecution` for jobs that must not overlap for the same JobDetail.
- Make jobs idempotent to tolerate duplicates or retries.

## Persistence & clustering

- Use Quartz JDBC JobStore (configure in `application.yml` or Quartz properties) and point all app instances to the same DB to enable clustered scheduling.

## Implementation checklist

- [ ] Define `schedule_config` table and run Quartz schema for your DB.
- [ ] Map `jobType` values to Job classes in `ScheduleService`.
- [ ] Implement CRUD admin endpoints and permission checks.
- [ ] Implement scheduling, rescheduling, pause/resume, and manual trigger logic.
- [ ] Add observability: metrics, job failure logs, retry counters, and alerting.

## Tips & gotchas

- Avoid large payloads in `JobDataMap`; pass IDs instead.  
- Use consistent naming for JobKey/TriggerKey — embed DB id.  
- Test misfire behavior under simulated downtime.  
- Use database transactions carefully: persist config first, then schedule with Quartz to avoid race conditions.
